# CAMS test case catalogue

All cases are initially NOT RUN. Use fixtures and environments in [the plan](TEST-PLAN.md). Each numbered case is a family: record a separate result for each role, input boundary, failure mode and environment variant; do not mark the whole family passed after one happy path. U = unit, I = integration, E = browser/system, W = interactive Windows, R = release/artifact.

For each case: reset fixtures; record initial state; perform steps; check UI/API response AND persisted state/events where relevant; collect evidence; restore fixture. Existing suites are starting points listed in the inventory, not evidence of completion.

## Detailed first classroom acceptance walkthrough

1. Snapshot the server and two clients. Build/package candidate and record installer hashes. Install server and initialize synthetic Admin; install its public root in the intended client user context according to Deployment guide.
2. Create T1/T2, separate classes, S1/S3 and two available workstations. Log into the browser as each role with separate browser profiles. Confirm denied Admin-only pages for Teacher/Student.
3. Log S1 and S3 into separate Windows clients. Confirm two connected clients, unique active station allocations and correct per-student session displays.
4. Open Teacher monitoring. Confirm intentional lab-wide visibility for both students; compare known visual markers on each desktop. Confirm scoped historical/detail operations separately.
5. Start/pause/resume/end sessions and check persisted state after refresh. Attempt a conflicting second login and verify rejection without changing the first allocation.
6. Add a harmless test app/domain rule. Confirm correct policy behavior, telemetry and alert. Acknowledge and reopen using allowed scope; verify the other student's alert cannot be changed through a scoped endpoint.
7. Send warning and briefly control only S1. Verify S3 receives neither. End control, confirm input stops and inspect command attribution.
8. Disconnect S1 for ten minutes while generating synthetic telemetry; reconnect. Record queue limits, replay behavior, connected count and continued session state. Restart server and repeat session reconciliation.
9. Export known data and compare totals/timestamps with the fixture. Back up then restore in the isolated environment and compare logical records.
10. Execute lock/logout/restart/shutdown only as separate snapshot-backed cases; perform installer upgrade/uninstall and rollback rehearsal. Finish report with every variant's status and remaining defects.

Map every service branch to relevant cases and automated method names. Map every Razor view and authored JavaScript file to UI-01 plus its business case. Map migrations/models to DB-01 and their domain case; contracts to HUB/TEL/POL cases; workflows/installers to BLD/INS/DEP. Mark an inventory row reviewed only after this mapping has evidence. Existing broad suites do not automatically close a row.
